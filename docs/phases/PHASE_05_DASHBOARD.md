# Phase 5 — Dashboard

**Status: Complete and verified**

Scope taken from `Hari_OS_V1_PRD.docx` sections 1.2 and 6.1. This document does not expand it.

## Purpose

Make the day's state visible in one place, and answer four questions in order: what matters
today, what needs attention, what changed, and what to do next.

## Scope

The PRD's Dashboard is described as a combination of: today's top 3 tasks, a suggested first
action, low-stock items, laundry/dishes status, today's spend, and an "I feel like scrolling"
entry point to the full Skills list.

Those six cards assume five modules. Two of them exist — Kitchen (Phase 3) and Expenses
(Phase 4). Routine, Sleep, Skills, Habits, and Photo Diary do not. Phase 5 therefore completes
the Dashboard from **real application state** and states plainly what is not available yet,
rather than building the missing modules to fill the screen.

## Dependencies

- Phase 1 complete: schema and a working data path.
- Phase 2 for the shared natural-language input.
- Phase 3 for kitchen stock, thresholds, and low stock.
- Phase 4 for accounts, expenses, today's spend, and the daily bill.

## Boundaries

- **Read-only.** The Dashboard has no endpoint and no mutation path of its own. Every change
  goes through `POST /api/commands` or `POST /api/kitchen`.
- **No recommendation engine.** The assistant organises; the user decides. Nothing on the page
  is ranked, scored, predicted, or generated by a model.
- **No fabricated data.** A future module that does not exist produces an unavailable state, not
  a zero, not an empty list, and not a sample row.
- **No duplicated rules.** Low stock is the domain's `isLowStock`; today's spend is the domain's
  `summariseDay`, the same function that produces the daily bill.
- No analytics, charts, trends, streaks, or scores.

## Expected deliverables

- Dashboard feature slice under `src/features/dashboard/`.
- A server-side read model composing the owning features' read sides.
- A page ordered by the questions above, with useful empty states.
- Read-side queries for the aggregated figures, each owned by the feature that owns the data
  rather than reimplemented here.

### The read model

`readDashboard(date)` is the only thing the page reads. It composes:

| Shown | Source | Rule applied |
| --- | --- | --- |
| Low stock | `listKitchenStock()` | the domain's `isLowStock` |
| Today's spend | `readDailyBill(date)` | the domain's `summariseDay` |
| Tasks | `display.tasksForDate(date)` | none; first three rows, count kept |
| Suggested first action | the same task rows | first not-done, or nothing |
| Dishes and laundry | `display.habitsForDate(date)` | none; rows or "not recorded" |
| Skills | a build constant, `false` | none |

The Dashboard's spend figure and the daily bill's total are the same number by construction,
not by agreement: both come from `summariseDay` over the same rows. `spendForDate`, the SQL
aggregate, exists in the repository and is **not** used here — a second way to total a day is
the exact failure Phase 4's architecture notes describe.

### Truthful states for what does not exist

- **Tasks.** `plan_task` has been in the schema since micro-phase 1.1, so real rows are read and
  displayed. Nothing in `src/` creates one, so the list is empty until Routine exists, and the
  page says that instead of implying a good day or a bad one.
- **Suggested first action.** The first task not marked done. Not ranked, not generated, and
  absent when there is nothing planned or everything is finished.
- **Skills.** No route, no list, no auto-selected replacement. The entry point states that the
  module does not exist yet.
- **Dishes and laundry.** `habit_log` exists, so its rows are read and shown. Nothing writes
  one, so an absent row reads as **not recorded** — which is a claim about the data, not a
  verdict about the user's day.

### Empty and first-run behaviour

The Dashboard renders on a database that has been migrated and never set up: no accounts, no
items, no expenses, no tasks, no habits. `npm run db:setup` is still the only way to create the
three accounts and the example items, and nothing is created as a side effect of opening a page.

### Security and architecture

Three boundary scopes are now enforced in addition to the existing ones, and
`npm run architecture:probe` asserts each one fires *and* that the imports the architecture
permits still pass:

- `src/features/dashboard/**` may not import `@/lib/db`, `better-sqlite3`, `node:fs`, a
  provider module, `@/commands/executor`, or a feature's write side.
- `src/app/**` may not import `@/lib/db`, `better-sqlite3`, `node:fs`, or the provider's config
  and transport modules. `next/server` is exempt, because every route handler needs it; the
  framework is not storage.

The Origin/Host guard on both write routes (ADR-042, ADR-045) is unchanged and is re-asserted by
both new test scripts.
