# Phase 8 — Photo and Diary

**Status: Complete — the diary, its notes, and the PWA half are delivered and verified.**

**What this phase resolved, 2026-10-01.** The scope note below asked the user one question — is a
diary entry a photo, a note, or a row of its own? — and it was answered as part of the work rather
than deferred: **a diary entry is the photo**. `habit_log` gained a nullable `photo_note`
(migration `003_diary_note`), `/diary` is the timeline of those photos with the user's own words
beside each one, and no diary table exists (ADR-056). Two further decisions came with it: notes are
written by forms and never by a sentence (ADR-057), and an entry's id stays with its entry
(ADR-058).

**The PWA half, delivered 2026-10-01, session 07.** Installability was built with no new
dependency, because the platform was already sufficient and a package would have added a
dependency tree to an application that currently has none (ADR-059). What shipped:

- `src/app/manifest.ts` — generated by the framework, not a static file, so the icons and the
  colours cannot drift from the source that knows them.
- Five PNG icons generated by `scripts/generate-icons.mjs`, which writes raw pixels with
  `node:zlib` and no image library. It is deterministic: the same command produces byte-identical
  files, so the icons are reviewable as a diff and reproducible on any machine.
- `public/sw.js` — install and activate handlers and nothing else. No `fetch` listener, no cache,
  no background sync, no push. A service worker that caches nothing cannot serve a stale diary, and
  that was a deliberate choice, not a gap (ADR-059).
- `src/app/service-worker-registration.tsx` — a client component that registers the worker in a
  production build only. Development is left alone deliberately: a worker that outlives a reload
  serves yesterday's application while a rule is being changed.
- Camera capture through the existing upload endpoint: the same form, the same validation, the same
  storage, with `capture` telling a mobile browser to open the camera rather than the gallery.

The phase also tightened two boundary gaps that its own client component exposed: a route or a
client component could import `@/lib/db` as a directory, and nothing in `src/app` refused the command
executor. Both are now refused, with one named exception for the command endpoint itself
(ADR-060).

**Scope note added 2026-10-01, after Phase 7.** The first two scope items below were delivered by
Phase 7, not deferred to this phase: `POST /api/photos` and `GET /api/photos/<id>/<filename>` write
and serve real pictures under `data/uploads/`, with magic-byte validation, server-generated names, a
size limit, and no path ever stored (ADR-051). Laundry cannot be completed by a sentence alone, and
`/habits` shows a Photo Diary timeline of those pictures.

This note is kept as written, because it records what was true when the phase had not started. The
question it ended with has since been answered; see ADR-056.

Scope taken from `Hari_OS_V1_PRD.docx` sections 6.6 and 1. This document does not expand it.

## Purpose

Turn laundry from a text claim into visible evidence, and build the visual diary that the
PRD describes as a timeline of laundry photos and daily notes.

## Scope

- **Laundry photo proof.** PRD section 6.6: the application does not accept a text claim alone.
  **Delivered in Phase 7** — there is no placeholder left to replace.
- **Local filesystem upload storage.** Files land under `data/uploads/`, never in `public/`
  (ADR-001; the PRD's Supabase Storage option was rejected in favour of the local
  filesystem). **Delivered in Phase 7**, in `src/lib/storage/photos.ts` with the feature slice
  owning every write (ADR-051, ADR-055).
- **Photo access through the PWA**, using the installable-app and camera access the PRD
  requires in sections 1 and 7. **Delivered** — the manifest, icons, and a service worker that
  registers for installability, plus `capture` on the upload form for the camera. No offline
  behaviour, deliberately (ADR-059).
- **A visual diary**: the PRD describes the laundry photo and daily notes forming a visual
  timeline. **Delivered** as `/diary`.

## Dependencies

- Phase 1 complete: schema and a working data path. **Done.**
- Phase 7 provides the laundry habit that the photo attaches to. **Done.**
- `src/lib/storage/` becomes real. **Done in Phase 7**; it holds `photos.ts` and a README that has
  been updated to say so.
- A PWA package is likely required here for installability and camera access. Phase 0
  deliberately added none (ADR-003). **Resolved without one.** The dependency was not needed:
  installability required a manifest, icons, and a registered worker, all of which the framework
  and the platform already provide, and camera access required an attribute on an existing form
  rather than a library (ADR-059).

## Boundaries

- **No upload logic is implemented in this document's phase planning.** This is a plan.
- **Uploads never go in `public/`.** Private user data stays in `data/uploads/`, which is
  git-ignored.
- **No cloud storage, no object store, no third-party media service.** ADR-001 fixed
  local filesystem storage; changing it requires a new ADR.
- No image recognition, tagging, or automated classification. The PRD does not ask for it.
- No video.
- Uploaded files are user data and must never be committed.
- **No caching in the service worker, and no offline mode.** A cached diary is a diary that can be
  wrong, and this application exists to show reality (ADR-059).
- **No generated diary text.** No captions, no summaries, nothing a language model wrote standing in
  for the user's own words (ADR-057).

## Expected deliverables

- Storage implementation in `src/lib/storage/`, respecting the boundary that all filesystem
  access lives there. **Done in Phase 7.**
- Photo upload attached to a laundry habit entry. **Done in Phase 7.**
- The visual diary view. **Done** — `/diary`.
- A PWA manifest, service worker, and icons, with the ADR recording the package choice. **Done** —
  the ADR records that the choice was *no package* (ADR-059).
- `data/uploads/` created on demand, as `data/` already is. **Done in Phase 7.**

session 07. Nothing here is a plan.

- A real photo is uploaded, stored under `data/uploads/`, retrieved, and displayed. **Verified** by
  `npm run diary:accept`, which uploads, saves a note, reads the diary back, and fetches the stored
  bytes.
- `git check-ignore` proves `data/uploads/` and its contents are untracked, including after a real
  upload exists. **Verified** against real files, not the pattern text.
- **No uploaded file appears in `git status`, in any commit, or in the build output.**
  **Verified**, including after the acceptance run created real uploads.
- `public/` is demonstrated to contain no private user data. **Verified** — `public/` holds five
  generated icons and the service worker, and nothing else that this phase added.
- **The app installs and launches, and the camera or file picker works on the target device.**
  Verified as far as a headless machine can: the browser parses the manifest, fetches every icon
  the manifest names, registers the worker, and the worker activates with the origin's scope. The
  camera itself cannot be exercised without a device, and that limit is stated rather than papered
  over — the form carries `capture`, which is the whole of what the platform asks for.
- The diary renders with no photos and does not crash. **Verified** by the acceptance run against a
  fresh database.
- Uploading a non-image file or an oversized file fails visibly rather than silently.
  **Verified** by `npm run diary:accept` and the photo unit tests.
