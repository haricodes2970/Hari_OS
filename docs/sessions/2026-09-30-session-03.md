## Money behaviour

Money is a whole number of minor units, 100 per rupee, exactly as ADR-021 chose. The domain
never does floating-point arithmetic on money.

`toMinorUnits` reads the decimal string instead of multiplying, because multiplying is where
rupee conversion normally fails: `1.15 * 100` is `114.99999999999999`. An amount with more
than two decimal places is **rejected, not rounded** — half a paise has no meaning, so
accepting it would silently invent a different number of paise than the caller wrote.

## Quantity behaviour

Six decimal places. Inputs beyond that scale are rejected; only the *result* of arithmetic is
rounded, exactly once. `0.1 + 0.2` is exactly `0.3`, and re-applying an operation to its own
output changes nothing.

This resolves the deferral in ADR-024, which accepted float error and left the rounding to
the domain layer. The error is bounded, not eliminated: binary floating point still cannot
represent most decimals exactly, so fractional stock carries an error below one millionth of
a unit — far below any kitchen measurement. That limitation is documented in `quantity.ts`
rather than hidden.

## A real bug the tests caught

A zero-amount spend produced a delta of `-0`. `Object.is(-0, 0)` is false, so the delta was
not equal to the plain `0` the test expected, and `-0` serialises inconsistently between
runtimes. The arithmetic was correct in every operation that matters, but the representation
was wrong.

Fixed with `normaliseZero` in `decimal.ts`, applied to every computed delta, so the sign
cannot be reintroduced at an individual call site. The domain now normalises at four points:
consumption, restock, recount, event replay, stamping, and reversal.

## Two design corrections made during review

- `reverseInventoryChange` originally returned an object with a zero delta when reversal was
  impossible — a silently incorrect result. It now returns a `Result` and reports the
  failure instead.
- `setAccountBalance` originally fabricated an `expense` row to satisfy a shared change type.
  A correction can move a balance *upwards*, so that row would have violated the schema's
  `amount >= 0` CHECK. The types were split: `AccountChange` for a correction with no row,
  `ExpenseChange` for a real spend.

## Error model

Seven codes in a closed union: `invalid_quantity`, `invalid_money`,
`invalid_money_precision`, `invalid_unit`, `insufficient_inventory`, `unknown_item`,
`missing_account`. Callers switch on `code`, never `message`. A test asserts that every code
is reachable from a real operation, so the set cannot drift into documentation that lies.

Notably absent: any code for a database error. Domain code cannot cause one, so no code
exists for it.

## Correctability, and where it does not work

Inventory is logged as signed deltas, so `reverseInventoryChange` produces an **exact**
compensating change. An event and its reversal replay to the original quantity.

The expense ledger cannot do this, and the code does not pretend it can. `expense` holds
non-negative spends only: there is no income row, no refund row, and no reversal column, and
`expense` has no `source_text` either. So there is nowhere for a correcting entry to live.

I did not invent a mechanism. Fixing it means a migration, which is not this micro-phase's
job, and it is recorded as a carried-forward limitation in `PROJECT_STATUS.md` and
`PHASE_01_FOUNDATION.md`.

## Two rules the PRD does not contain, deliberately not invented

- **No `insufficient_balance` error.** Spending more than the balance is allowed and lands
  at exactly `before - amount`. ADR-021 decided a negative balance is a real state, and the
  PRD never says a spend must be affordable. Inventing an affordability rule would be
  inventing a business rule. The behaviour is pinned by a test either way.
- **No unit conversion.** `piece` is not `kg`, and the domain does not attempt to know
  whether `g` and `kg` are convertible. Canonicalising what a user wrote belongs to whatever
  introduces the item.

## Determinism audit

Searched `src/domain` for floating-point money arithmetic, implicit clock reads, random ids,
global mutable state, filesystem access, environment access, SQLite imports, network access,
and mutation of caller-owned objects. Result: none present. The only multiplication in
`money.ts` is the integer fast path guarded by `Number.isInteger`.

Two mechanisms back this up rather than relying on the audit alone:

- **Enforced by lint.** The `hari-os/domain-purity` rule blocks `node:fs`, `node:os`,
  `node:path`, `node:child_process`, network modules, `better-sqlite3`, `server-only`,
  `next/*`, `@/lib/db`, `@/lib/storage`, `@/commands`, plus `process.env`, `Date.now`, and
  `Math.random`. Proven with a temporary probe file that triggered all seven restrictions,
  then deleted. A guard nobody has seen fire is a claim, not a control.
- **Proven independent of SQLite.** `better-sqlite3` was moved out of `node_modules` and
  `npm run domain:test` still passed 170/170, then the driver was restored. The boundary is
  not merely respected by inspection; the suite cannot reach a database by any path.
