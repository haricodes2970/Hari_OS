# Session 08 — Phase 8: the installable application, with nothing added and nothing cached

**Date:** 2026-10-01
**Phase:** 8 — Photo and Diary (completing it)
**Outcome:** Delivered and verified. Phase 9 was not started.

## What this session was for

Session 07 built the diary and left the phase document's PWA items undone: installability, camera
access, a manifest, a service worker, icons — and a package choice to be recorded as an ADR first.
The document predicted that a PWA package would be "likely required," and that prediction is the
thing this session had to test rather than repeat.

## The prediction was wrong, and testing it was the work

The requirement a browser checks before offering to install is three things: a manifest served from
the origin, icons that resolve, and a service worker whose scope covers the start URL. All three are
platform features. The camera is one attribute on the file input the application already had. So
`next-pwa` and `serwist` — both of which wrap the build, generate a worker with a precache
manifest, and inject a registration component — would have bought a build-time plugin and a
dependency tree in exchange for behaviour this application does not want (ADR-059).

**The worker caches nothing.** That is the substantive decision, not the package one. Cache-first
for the shell and network-first for data is the conventional PWA, and here it is wrong: a cached
`/diary` is a diary that can be wrong. A note the user cleared, a photo they deleted, a habit they
re-recorded, all still visible from a cache that nothing invalidates correctly. This application
exists to show reality. So `public/sw.js` has `install` and `activate` handlers and no `fetch`
handler at all — not even a pass-through. Every request is served by the network, exactly as it would
be with no worker, and a stale response is not possible because nothing is ever held.

There is no offline mode. That is a decision, recorded in the ADR so a later phase does not read the
absence as work left undone.

## What was built

| File | What it is |
| --- | --- |
| `src/app/manifest.ts` | The manifest, generated by the framework from source rather than a static file |
| `scripts/generate-icons.mjs` | Writes five PNGs with `node:zlib` and no image library |
| `public/icon-{192,512}.png`, `icon-maskable-512.png`, `apple-touch-icon.png`, `favicon.png` | Its output, committed so no build is needed to serve them |
| `public/sw.js` | Install and activate. Nothing else. |
| `src/app/service-worker-registration.tsx` | A client component; registers the worker in a production build only |
| `scripts/pwa-test.mjs` | 61 assertions on the manifest, the icons, the worker, and the camera form |
| `scripts/pwa-accept.mjs` | 55 assertions against a real production build over HTTP |

**The icons are generated, not drawn.** Committing PNGs from a design tool puts binary files in a
repository nobody can diff, and lets the icon drift from whatever claims to produce it. The generator
is deterministic, and `pwa:test` proves that by regenerating every icon into a temporary directory
and comparing bytes — so the files in `public/` are provably the script's output.

**Registration is production-only.** `npm run dev` is never served by a worker holding a previous
build. That is the failure mode that makes PWA development miserable, and it is one line of
`process.env.NODE_ENV`.

**Camera capture is an attribute.** The upload form has two inputs over one endpoint: `capture` opens
the camera on a phone, and the ordinary file field is what a desktop uses. Both pass the same origin
guard, the same magic-byte validation, and the same storage. There is no second endpoint and no
second write path (ADR-051).

## The boundary gap the client component exposed

`src/app/service-worker-registration.tsx` is the first file in this project that runs in the user's
browser. Writing it made two gaps in the `src/app` lint scope obvious, and both were there before
this session:

- The scope refused `@/lib/db/connection`, `@/lib/db/migrations`, `@/lib/db/schema` — specific
  modules — but not the `@/lib/db` directory. Every other layer in the project refuses that
  directory wholesale; `src/app` was an accident of enumeration.
- Nothing refused `@/commands/executor`. A route holding the executor can write through any feature,
  bypassing the feature's own route, the origin guard, and the outcome mapping.

Both are refused now, with `src/app/api/commands/route.ts` named as the one exception (ADR-060).

**One attempt failed and is recorded rather than hidden.** The first attempt used `overrides` inside
`no-restricted-imports` to scope the exception. ESLint 9.39 has no such key, and a rule object
carrying one fails to *load* — which fails the entire lint run rather than the intended check, and
for a few minutes left every boundary probe failing at once. The second attempt, a separate config
object, would have been worse and quieter: `no-restricted-imports` replaces its pattern list rather
than merging, so an object carrying only the new executor pattern would have removed the nine
existing rules from every file it matched. The patterns are now a shared constant used by both
expressions, so they cannot drift.

## What was verified, and what was not

Everything below was run in this session. Nothing is a claim about a check that was skipped.

| Check | Result |
| --- | --- |
| `npm run format:check` | pass |
| `npm run typecheck` | pass |
| `npm run lint` | pass |
| `npm run build` | pass; `/manifest.webmanifest` emitted as a static route |
| `npm run db:check` | pass, including the `photo_note` column |
| `npm run db:test` | 53 passed |
| `npm run domain:test` | 278 passed |
| `npm run diary:test` | 69 passed |
| `npm run skills:test` | 150 passed |
| `npm run exec:test` | 76 passed |
| `npm run pwa:test` | 61 passed |
| `npm run pwa:accept` | 55 passed |
| `npm run architecture:probe` | 82 passed |
| `npm run responsive:check` | 61 passed, at 320, 390, and 1440px |

**Verified in a real browser, not by inspection.** `responsive:check` drives a headless Chrome
against the production build and asks what the *browser* decided: the document links a manifest, the
browser parses it, it names two icons and a maskable one, all three resolve, the worker registers
with the origin's scope, the script behind it is the one served from the root, and it reaches the
`activated` state. Then the check that the worker changed nothing: after exercising the application,
`caches.keys()` is empty and `caches.match('/diary')` is undefined, while the page just fetched is
live — it contains the note the test wrote. A worker that cached anything would fail that.

**Data safety, checked against real files.** `data/hari-os.db` is byte-identical after the acceptance
runs, no WAL or SHM sidecar appeared, the disposable database and its directory were removed, and
every upload the run created was removed. `public/` contains the five icons and `sw.js`, and no
private data.

**One assertion was wrong, and it was the test that was wrong, not the app.** `pwa:accept` asserted
that the page requests no `/favicon.ico`, on the theory that none exists. Next.js 16 serves a default
favicon at both `/favicon.ico` and a hashed variant, with HTTP 200 and `image/x-icon` — so the
assertion demanded something untrue. It now parses the head, collects every `rel` of `manifest`,
`icon`, or `apple-touch-icon`, and asserts each one resolves with bytes behind it. That is the claim
that matters to a browser, and it catches a broken icon link, which the old assertion could not.

**Not verified, and not claimed.** Installing the application needs a `beforeinstallprompt`, which
requires a user gesture and a real browser profile; no script can raise it. Opening a camera needs a
device. What is verified is every installability requirement observable from outside a browser, and
the `capture` attribute on the form — which is the entirety of what the platform asks of a
developer. The last mile is a phone test, and it is carried forward in `PROJECT_STATUS.md` as an open
item rather than quietly dropped.
