### D. Error handling

State was captured before and after all seven attempts as
`onions|cash|expense rows|event rows`.

| Attempt            | Outcome                          | Banner rendered |
| ------------------ | -------------------------------- | --------------- |
| Invalid command    | `err=invalid_command&field=kind` | Check the "kind" value and try again. |
| Unknown item       | `err=unknown_item`               | Not in your kitchen yet. |
| Unknown account    | `err=invalid_command&field=accountName` | Check the "accountName" value. |
| Insufficient stock | `err=insufficient_inventory`     | You do not have that much. |
| Unit mismatch      | `err=invalid_unit`               | That unit does not match. |
| Empty amount       | `err=invalid_command&field=amount` | Check the "amount" value. |
| Negative amount    | `err=invalid_command&field=amount` | Check the "amount" value. |

State after: `6|-6000|1|1` — **identical to before**. No failure partially mutated anything.

**Persistence failure** is covered by `exec:test` rather than repeated here, because forcing a
real storage failure over HTTP is not possible without adding a fault-injection path to the
application. Those 76 tests produce genuine mid-transaction failures with a `BEFORE INSERT`
trigger that raises, and assert the rollback: "the account balance was rolled back: no money
vanished without a record", "no expense row survived the rollback", and "the quantity write
was rolled back, so no unexplained number is left behind".

**Empty states.** Against a database that was never set up, all three pages returned **HTTP
200** with explicit empty states — Dashboard 2, Kitchen 1, Expenses 2 — each worded as a
normal state rather than an error.

the typos: a documentation edit that reports success without having applied is worse than no
edit, because it leaves the contradiction in place while the log claims it was resolved. Every
replacement in this micro-phase was verified by re-reading the file afterwards.
