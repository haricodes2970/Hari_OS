## Objective

Establish the validated structured-command contract that will later sit between
natural-language parsing and deterministic domain execution — without executing anything or
persisting anything.

## The four commands

`inventory.consume`, `inventory.restock`, `inventory.set_quantity`, `expense.record`.

Each carries only what the user stated, plus a `version` literal and the originating sentence
as `sourceText`. Routine, sleep, skills, and habits are absent because no domain operation
exists for them, and a command type with no execution path is a promise the code cannot keep.

## The central decision: facts, never results

The tempting design is a command carrying what *will* happen — the new balance, the remaining
stock — so the UI could preview it for free. I did not build that.

A computed outcome inside the command would place an unverified number inside the trust
boundary, with nothing between it and the database. The PRD requires balances and quantities
to be decided by deterministic code, and a preview number is exactly the kind of value that
gets trusted because it is already there. A test asserts a validated expense command contains
no such field.

Two smaller absences follow the same logic:

- **No ids.** A model reading "used 2 onions" cannot know a row id, and asking one to invent
  an id is asking it to fabricate a fact. Resolution is execution's job and produces a domain
  failure when nothing matches.
- **No timestamp.** The moment a spend happened is the moment the user logged it, not the
  moment a model finished responding.

## Validation and domain errors are different types

`ValidationResult` mirrors the shape of the domain's `Result` but is deliberately a different
type. Conflating them would be a real bug waiting to happen: a caller asking "why was this
rejected?" could not distinguish "the model sent something malformed" from "there are only 3
onions". Those need completely different responses — one is a contract problem, the other is a
fact the user needs to hear. Keeping them separate makes the confusion a compile error.

Validation checks structure. It does not check existence, because that needs the database, and
a validator that queried SQLite could not be called from a test, a form, or a client
component. It also computes nothing.

Representation checks reuse the domain's own exported predicates — `isMoneyAmount`,
`isQuantity`, `isAccountName` — rather than re-implementing them, so the command boundary and
the schema `CHECK` constraints cannot drift apart.

## A real robustness defect, found by a hostile-input test

The first test run included an object with a getter that throws, and `parseCommand` **threw**.
A validation boundary that can be crashed by the input it is inspecting is broken: an
exception escaping there takes down whatever request or form triggered it, which is precisely
the outcome validation exists to prevent.

Fixed by wrapping the read in a `try` and converting any failure into a rejected command, with
whatever issues were already found kept alongside. The boundary now fails closed on every
path.

That was the only way this surfaced. Every other hostile case — null, arrays, a bare sentence,
`__proto__` from parsed JSON, inherited fields — was already handled, and a test asserting "it
returns a result rather than throwing" would have passed while the getter case still crashed.

## Fail-closed choices worth naming

- **Unknown fields are rejected, not dropped.** A producer inventing an `amount` or a
  `balance` is a producer not following the contract, and silently dropping the field would
  hide exactly the drift worth noticing. Tests confirm an invented `balance` and an invented
  `timestamp` are both refused.
- **Only own properties are read.** A `value[key]` read would happily return an inherited
  property, so a poisoned prototype could present a `kind` the object never declared. Tests
  cover inherited `kind` and inherited `amount`.
- **All issues at once.** The usual caller is a model that has to retry; one problem per
  attempt turns a two-error payload into two round trips.

## Two boundary rules added to lint

`hari-os/validation-purity` and `hari-os/command-boundary` share one definition of impurity.
Both block database, filesystem, network, environment, and clock access.

`src/commands` is **not** blocked from importing `src/domain`, because `ARCHITECTURE.md`
section 4 explicitly permits it. Blocking it would pre-empt a decision belonging to the
execution micro-phase. The distinction enforced is the one the architecture states plainly:
the command layer proposes and validates, and does not persist.

## Proving it rather than asserting it

- **Lint rules fire.** Two probe files triggered nine violations across both rules, then were
  deleted. A guard nobody has seen fire is a claim, not a control.
- **The boundary cannot reach SQLite.** `better-sqlite3` was moved out of `node_modules` and
  both the domain (170) and contract (93) suites passed unchanged, then the driver was
  restored.
- **The type-level proof bites.** `domain-input.ts` asserts that each adapter's return type is
  exactly `Parameters<typeof theDomainOperation>`, so a renamed field becomes a compile error.
  Injecting a drift — an extra argument — was confirmed to fail `tsc`, then reverted.
- **No LLM anywhere.** `package.json` and `node_modules` contain no provider SDK, and no
  vendor name appears in the contract.

- **No parser**, no regex parsing, no prompts, no OpenRouter, no LLM, no chat routing.
- **No routes, no server actions, no feature modules, no UI.**
- No change to migrations, schema definitions, or seed data.
