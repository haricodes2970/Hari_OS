## Micro-Phase 0.2 — Next.js Foundation

**Objective:** Establish a Next.js + TypeScript application foundation that starts locally,
builds for production, and is ready to become a localhost PWA. No product features.

### Implementation details

Scaffolded with `create-next-app@16.3.7` in a **temporary directory**, then copied the
resulting files into the project. This was deliberate: the project directory is not empty
(it holds `.git`, `docs/`, and the PRD), and scaffolding in place risked overwriting existing
work. The scaffold's own `.gitignore` was merged into the existing one rather than replacing it.

| Choice | Value | Reason |
| --- | --- | --- |
| Next.js | 16.3.7 | Current stable release |
| React | 19.2.8 | Pinned by the Next 16 scaffold |
| Router | App Router | Server Components allow future SQLite access server-side |
| Structure | `src/`, alias `@/*` | Keeps app code separate from root-level config |
| Package manager | npm 10.9.8 | Per instructions; no pnpm |

### Problems encountered

**1. `TS2304: Cannot find name 'LayoutProps'` — fixed.**
The Next 16 scaffold types the root layout as `LayoutProps<"/">`, a global type generated into
`.next/types`. It does not exist until `next dev` or `next build` has run, so `npm run typecheck`
failed on a clean tree. This was a real failure caught by verification, not a theoretical one.
Fixed by typing the layout explicitly as `{ children: ReactNode }` (ADR-007). Typecheck was then
re-run after `rm -rf .next` and passes from a clean checkout with no prior build.

**2. `npm warn deprecated eslint@9.39.5` — not fixed, upstream.**
`eslint-config-next@16.3.7` depends on `eslint@^9`, which npm reports as deprecated. This is not
a warning introduced by this project; it comes from the framework's own dependency range. Pinning
to a newer major risks breaking `eslint-config-next`. Left as-is and recorded in
`PROJECT_STATUS.md` under Known Issues.

**3. Network interruption during the session.**
The user's network dropped partway through. No verification step had failed as a result — all
checks had already passed. The typecheck, lint, and build were simply re-run afterwards from a
clean state to confirm nothing regressed, and all passed again.

## Micro-Phase 0.3 — Development Tooling

**Objective:** Establish clean, consistent development tooling with a minimal dependency
surface. No feature work, no SQLite, no architecture work.

### Implementation details

**Prettier added** as the single dev dependency of this micro-phase: `prettier@3.9.9`.
Prettier 4.0.0 exists only as an alpha (`4.0.0-alpha.13`) and was deliberately not used.

`.prettierrc.json` states the formatting contract explicitly — `printWidth` 80, semicolons,
double quotes, `trailingComma: "all"`, 2-space tabs, LF line endings. These match Prettier's
own defaults, so the file documents intent rather than overriding it. The code written during
0.2 already conformed: 7 of 9 files were reported `unchanged` on the first run.

`.prettierignore` excludes `package-lock.json` (not ours to format), `docs/` and the PRD
(historical record, not application code), plus `public/`, build output, `data/`, and
dependencies. See ADR-010.

**ESLint integration: deliberately not added.** `eslint-config-prettier` is the conventional
guarantee against Prettier and ESLint disagreeing, but it was only added if genuinely
necessary. Two checks established it was not:

1. `eslint-config-next@16.3.7` ships no core formatting rules — a grep for `quotes`, `semi`,
   `indent`, `comma-dangle`, `max-len`, `arrow-parens`, `object-curly-spacing` returned
   nothing, and there is no `@stylistic` integration.
2. A deliberately misformatted `src/app/__conflict_probe.tsx` was created. `prettier --check`
   flagged it; `eslint` exited 0 with no diagnostics. The probe file was then deleted.

The existing Next.js ESLint config was left completely untouched, and no lint rule was
weakened or disabled. See ADR-009.

**`next.config.ts` cleanup.** Prettier wanted to collapse the scaffold's placeholder comment
into a single mangled line (`const nextConfig: NextConfig = {/* config options here */};`).
Rather than accept that, the placeholder comment was replaced with a clean empty config, which
is Prettier-stable. This is cosmetic; no Next.js behaviour changed.

**Scripts added:** `format` (`prettier --write .`) and `format:check` (`prettier --check .`).
The existing `dev`, `build`, `start`, `lint`, and `typecheck` scripts were left as they were. No
aggregate `verify` or `test` script was added — there is no test runner in Phase 0 and no CI,
so such a script would have no current purpose.

## Micro-Phase 0.4 — Application Architecture

**Objective:** Establish the directory boundaries later phases build on, so that feature
work does not couple UI directly to SQLite or to the LLM. No feature work, no SQLite.

### Implementation details

Seven boundary directories were created, each holding a short README that states what
belongs there and what must not:

```
src/app/            (pre-existing) routes and layouts
src/components/     reusable presentation
src/features/       vertical slices, one per product area
src/domain/         pure business rules and calculations
src/commands/       future natural language command engine
src/lib/db/         SQLite access boundary (arrives in 0.5)
src/lib/storage/    local filesystem boundary (Phase 8)
src/lib/validation/ input and domain validation
```

**What was deliberately not created**, to avoid speculative scaffolding:

- `src/types/` — a shared types barrel attracts unrelated types and couples features
  through it. Types belong to `domain/` or to the owning feature (ADR-012).
- `src/features/{dashboard,kitchen,expenses,skills,habits,routine}/` — empty subdirectories
  for unbuilt features are noise. They are created by the phase that implements them.
- Barrel `index.ts` files, service layers, and repository interfaces. No second caller
  exists yet for any of these.
- Any SQLite package, connection, schema, or query. None is needed to establish a
  boundary, so none was installed.
- Any parser, LLM SDK, or OpenRouter integration.

**Boundaries are enforced, not just described.** `eslint.config.mjs` gained a
`hari-os/boundaries` block using ESLint's built-in `no-restricted-imports`: files under
`src/domain/` and `src/components/` may not import `@/lib/db`, `@/lib/storage`, or
`@/commands`. This adds no dependency — `dependency-cruiser` and `eslint-plugin-boundaries`
were considered and rejected as unnecessary weight for two rules. See ADR-011.

The rule was verified with probe files rather than trusted on inspection:

| Probe | Expected | Result |
| --- | --- | --- |
| `src/domain/` importing `@/lib/db` | Error | Error reported |
| `src/components/` importing `@/commands` | Error | Error reported |
| `src/app/` importing `@/lib/db` | Allowed | Clean |
| `src/features/` importing `lib/db`, `lib/storage`, `lib/validation` | Allowed | Clean |

All four probe files were deleted. The rule constrains only the two layers where purity
is unambiguous, so it does not block the patterns 0.5 and later phases will need.

The `src/commands/README.md` records the rule that shapes the LLM boundary for the rest of
the project: the model interprets language and proposes a typed intent, while persistence
and arithmetic stay in deterministic code under `domain/`. This is the V1 principle that
balances and inventory quantities are never computed by an LLM, expressed as a code
boundary rather than a comment.
