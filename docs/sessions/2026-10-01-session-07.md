# Session 07 — Phase 8: the diary, and the notes that go with the photographs

**Date:** 2026-10-01
**Phase:** 8 — Photo and Diary (partial: the diary and its notes; the PWA work is not done)
**Outcome:** Delivered and verified. Phase 9 was not started.

## What this session was for

Phase 7 ended by shipping the photograph half of the PRD's diary sentence and leaving the other half
nowhere to go. `docs/phases/PHASE_08_PHOTO_DIARY.md` recorded that as a question for the user
rather than a decision: *is a diary entry a photo, a note, or a row of its own?* The work here
answered it — **the entry is the photo** (ADR-056) — and built the surface that reads and edits it.

## The decisions, and what would have happened otherwise

**A diary entry is the photo.** `habit_log.photo_note`, one nullable column, migration
`003_diary_note`. The rejected alternative was a `diary_entry` table, which would have had to carry
the photo reference as well: two records of one picture are two answers to "which image is this"
the day they disagree. A column makes "a note exists only where a photo exists" structural rather
than maintained, and `src/features/habits/diary.ts` is its single writer.

**No chat command for a note** (ADR-057). Two reasons, and the second is the decisive one. A
sentence cannot name which photo the user meant, so the interpreter would have to guess — and this
application does not guess: `habit.record` records laundry as *not done* when no photo can be
verified (ADR-053). More importantly, a note is prose, and the parser is a model whose prompt has to
*instruct* it never to summarise a `note`. Not routing the words through it at all is a stronger
guarantee than any instruction. Notes are written by forms: the Habits upload takes one with the
file, and `/diary` edits one in place.

**An entry's id stays with its entry** (ADR-058). Not a preference — a defect found while testing.
Phase 7 wrote a habit by deleting the row and inserting a new one, which was invisible for a habit
and, once the row carried a note, destroyed the note. Worse, SQLite hands out `max(rowid) + 1`, so
after the only row is deleted the next insert reuses its number: a `/diary` page open in one tab
could post a note to entry 3 while another tab replaced that row, and the note would land on a
different day's photograph with nothing reporting it. Both write paths now `UPDATE`, and
`deleteForDay` is gone.

## What was built

### Schema

Migration `003_diary_note`: `ALTER TABLE habit_log ADD COLUMN photo_note TEXT`. No rebuild, no
widened constraint, existing rows untouched. `schema.ts` gained the column and a comment saying why
it is absent from the table's `CREATE` statement.

### Domain

- `src/domain/diary.ts` — `diaryNote` (trim, 500 characters, control characters refused except tab
  and newline, empty means no note), `hasDiaryNote`, `DiaryEntry`, and `byNewestFirst` for a total
  order on days that were photographed twice.
- `src/domain/result.ts` — `invalid_diary_note` and `unknown_photo`.
- `src/domain/habits.ts` — `HabitLog` gained `photoNote`, and `HabitRecord` was introduced so
  `habitStreak` and `laundryProgress` ask for the three fields they read instead of a whole row.

### Persistence

`HabitRepository` gained `updateHabitForDay` (the update both write paths use), `saveDiaryNote`, and
`listDiary`, and lost `deleteForDay`. Every statement now names its columns through one
`HABIT_COLUMNS` constant, so a new column cannot be silently left out of a `SELECT`.

### Features

- `src/features/habits/diary.ts` — `readDiary`, `readDiaryEntry`, `writeNote`, `diarySummary`, and a
  three-way result that keeps a domain refusal distinct from a persistence failure.
- `src/features/habits/photos.ts` — the upload takes an optional note, validates it **before** the
  file is written, and preserves the previous note when a day is photographed again.
- `src/features/habits/view.ts` — `TodayEntry`, a projection with no note field, so the Dashboard
  has nothing to receive.
- `src/features/shared/outcomes.ts` — two new messages, worded as what to change.

### Routes and pages

- `POST /api/photos/[id]/note` — origin guard, form or JSON, 303 with a token or a JSON body.
- `POST /api/photos` — an optional `note` part.
- `src/app/diary/page.tsx` and a `Diary` nav link; `/habits` keeps a preview and links to it.
- `globals.css` — `.diary-photo` and `.diary-note` rules, which did not exist when Phase 7 started
  using them, so a wide photograph pushed the page sideways on a 320px screen.

## The boundary gap found here

`eslint.config.mjs` reported that `src/domain` and `src/components` may not import the layers above
them, and for `src/domain` it did not. `hari-os/boundaries` is shadowed for that scope by the
enforced block ADR-046 added — ESLint replaces a same-named rule wholesale rather than merging it —
so a domain module could import a feature, and reach a database through it, with `npm run lint`
passing. The pattern now lives in the enforced block, and `architecture-probe.mjs` probes it (74
probes, up from 58). The same probe run is what proved the rule *did* fire before it was moved: the
first version of the fix was added to the shadowed config and passed `lint` while catching nothing.

## Problems worth remembering

- **Three test failures were real defects, not test bugs.** The carried-note precedence was
  backwards (a note typed with a new upload lost to the old one), an unparseable JSON body was
  treated as "no note" and could therefore *delete* a stored note, and `readHabits` returned whole
  `HabitLog` rows — which, once the row carried a note, handed the Dashboard the diary note. The
  third is the reason `TodayEntry` exists.
- **A module-level `/g` regex is stateful across calls.** The first draft of `diaryNote` used
  `RegExp.prototype.test` on two shared `/g` patterns, so the *second* note checked in a process
  would test a different slice of the string. Both patterns are flagless or used only with
  `replace` now, and the domain suite asserts the same refusal twice in a row.
- **A truncated PNG stub is not a picture.** The responsive check measures whether a photograph is
  fitted to the screen, which needs an image the browser can decode; the 20-byte signature stub the
  other suites use left the `<img>` permanently unfinished. It also needed the lazy-loaded image
  scrolled into view before it would be fetched at all.
- **A leftover artefact was found and removed.** `data/uploads/responsive-check.png` from an earlier
  failing run. It was git-ignored, but it was not the user's file.
