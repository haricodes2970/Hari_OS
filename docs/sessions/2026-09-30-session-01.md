### SQLite implementation selected

`better-sqlite3@13`, with `@types/better-sqlite3` as a dev dependency and `server-only`
as a server-side guard. No ORM.

### Why, and what was rejected

Node v22.23.1 ships a built-in `node:sqlite`, which would have required **zero**
dependencies. It was tested before being rejected rather than dismissed:

```
$ node -e "const {DatabaseSync}=require('node:sqlite'); ..."
OK  sqlite version: 3.51.2
(node:9032) ExperimentalWarning: SQLite is an experimental feature and might change at any time
```

It works, but it warns on every run and its API may change without notice. Hari OS will
store financial balances and inventory quantities that V1 requires to be deterministic and
correctable, so a stable API is worth two packages.

### Design

One file, `src/lib/db/connection.ts`, holding infrastructure only:

- **Path** — `path.join(process.cwd(), "data", "hari-os.db")`, derived from the project
  root so no machine-specific absolute path is hard-coded. The optional
  `HARI_OS_DB_PATH` environment variable overrides it for tests and tooling. No other
  configuration was introduced (ADR-016).
- **Creation** — the directory is created with `mkdir -p` on first open, so there is no
  manual setup step and no committed database file.
- **Configuration** — `journal_mode = WAL` and `foreign_keys = ON` are set at open time.
  These are infrastructure concerns, not schema.
- **Singleton** — the handle is cached on `globalThis` so Next.js module reloads in
  development do not open a new connection on every reload.
- **Failure** — a failed open throws an error naming the resolved path.
- **Verification** — `checkDb()` reports path, SQLite version, journal mode, and foreign
  key state without writing.
- **Server-only** — the file starts with `import "server-only"` (ADR-015).

`next.config.ts` now sets `serverExternalPackages: ["better-sqlite3"]` so Next does not try
to bundle the native module.

### Verification script

`scripts/db-check.mjs`, exposed as `npm run db:check`. It imports the **real**
`connection.ts` rather than duplicating logic, and fails loudly if any Hari OS feature
table exists. It has lasting value as the reproducible check for this foundation, so it
was kept rather than deleted as a temporary probe.

Node runs the TypeScript module directly via native type stripping. Because `server-only`
throws outside a Server Component, the script runs with `--conditions=react-server`.

### Problems encountered

**1. `db:check` failed on first run — a real bug in the script.**
The script asserted the database file existed *before* calling `checkDb()`, but the file is
created lazily on first access, so the assertion always failed. The order was reversed:
open first, then assert existence. Confirmed by re-running from a directory that did not
exist.

**2. The env override produced a false failure.**
The "resolves inside the project root" assertion fired on a deliberate override, which
would have made the override unusable. The assertion now applies only to the default
path, and an override is reported as an accepted alternative.

**3. The `server-only` verification initially proved nothing — twice.**
- First attempt used an `_`-prefixed directory. The App Router treats those as private
  folders, so Next never compiled the probe and the build passed. That result was
  meaningless and was discarded rather than reported as a pass.
- Second attempt used an unreferenced file, which Next also does not compile.
- The third attempt used a real route and produced the expected build failure.

**4. `MODULE_TYPELESS_PACKAGE_JSON` warning.**
Running the standalone script made Node warn that it was reparsing `connection.ts` as an ES
module. Suppressing it was rejected as concealing a real signal. The root cause was fixed
instead by declaring `"type": "module"` in `package.json`, which was verified not to break
the build, typecheck, lint, or the check script (ADR-017).

**5. `server-only` throws in plain Node.**
Expected behaviour — it resolves to a throwing module unless the `react-server` condition
is active. `db:check` therefore runs with `--conditions=react-server`.

### No feature schema was created

Confirmed by querying `sqlite_master` inside `db:check`: the database contains **zero**
application tables. None of `plan_task`, `sleep_log`, `nap_log`, `inventory_item`,
`inventory_event`, `account`, `expense`, `skill`, `skill_log`, `habit_log`, or
`private_log` exists. `db:check` fails loudly if any of them ever appears, so a future
phase cannot quietly build schema during unrelated work.

No repositories, services, query functions, migrations, or seed data were created.

### Architectural decisions made

Four new ADRs, bringing the total to seventeen:

- **ADR-014** `better-sqlite3` over the built-in `node:sqlite`, with the evidence.
- **ADR-015** `server-only` as the server-side guard, with the verified build failure.
- **ADR-016** Optional `HARI_OS_DB_PATH` override.
- **ADR-017** `"type": "module"` declared to remove a warning at its source.

### Problems encountered

**1. The WAL sidecars were truncated during ignore testing.**
While proving that `data/hari-os.db-wal` and `data/hari-os.db-shm` were ignored, real files
were created at those paths, overwriting the live sidecars. This was expected — the check
demanded real files — but it touched live database state, so it was verified afterwards.
`npm run db:check` passed, and `integrity_check` returned `ok` with the schema still empty.
The sidecars are transient runtime files that SQLite recreates on demand, and the main
`data/hari-os.db` file was never modified. Restored state confirmed.

**2. Stale generated types broke `typecheck` after the probe routes were deleted.**
Deleting the `probetmp` probe route left a reference to it in the generated
`.next/types/validator.ts`, so `npm run typecheck` failed with
`Cannot find module '../../src/app/probetmp/page.js'` even though no such file existed.
This was a leftover build artifact, not a source defect. Clearing `.next` fixed it, and
`typecheck` now passes both on a clean tree and after a build. Worth remembering: deleting
a probe route leaves traces in `.next` until it is regenerated.

**3. `.env.example` could not be tested from the live clone.**
The file was uncommitted, so a clone could not contain it. Rather than skip the check, the
post-commit state was simulated in the clone and then verified for real against the remote
after pushing.

**5.** No other failures. The known upstream `eslint@9.39.5` deprecation persists and is
unchanged.
