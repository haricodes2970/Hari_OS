## Objective

Connect the validated command contract to real SQLite persistence, through an execution
boundary that keeps the domain pure and cannot leave partial state behind.

| File | Purpose |
| --- | --- |
| `src/lib/db/repositories.ts` | The only module that reads or writes application tables |
| `src/commands/executor.ts` | Sequences a validated command: resolve, decide, persist |
| `scripts/exec-test.mjs` | 76 integration tests against real SQLite (`npm run exec:test`) |

## The architectural checkpoint

Before writing anything, I listed what the four commands actually need, rather than building a
repository layer in the abstract. It is six methods and a transaction:

- `inventory.findByName`, `inventory.saveQuantity`, `inventory.appendEvent`
- `accounts.findByName`, `accounts.saveBalance`
- `expenses.insert`

That is the whole surface. No generic base class, no unit-of-work abstraction, no
table-per-repository convention. A repository method appears when a command needs it.

## The execution boundary

Three layers with distinct jobs:

- **`src/domain` decides.** Every balance, every remaining quantity, every refusal.
- **`src/lib/db/repositories.ts` stores.** No business arithmetic anywhere in it.
- **`src/commands/executor.ts` sequences.** Resolve names to rows, call the domain, persist
  the result.

The ordering is the design: **the domain runs before any write.** Nothing is written until the
domain has decided the outcome, so a refusal such as "only 3 onions" can never leave a
transaction open, and the executor never has to undo a change the domain declined to make.

The executor calculates nothing. Every number in its output arrived from `src/domain` or from
a column it just read.

## Three error vocabularies, kept apart

`validation` (the producer is broken), `domain` (a real-world impossibility, carrying codes
like `unknown_item` and `insufficient_inventory`), and `persistence` (the request was fine and
storage failed — the only case where retrying makes sense).

Repositories follow the same split: a read returns the domain's `Result`, because "no such
item" is a domain concept; a write returns `PersistenceResult`, because a write has no domain
failure to report.

## Identity and time are obtained, never supplied

A command carries no id and no timestamp. The id comes from the row the repository loaded; the
timestamp comes from an injected clock. Tests assert both: a command with an injected `id` or
`balance` is rejected as a validation failure, and two executions of the same command with two
different clock readings store two different timestamps.

The clock is injected rather than read from `Date.now()` so the executor stays deterministic
and the boundary rule needs no exception (ADR-034). A consequence worth stating plainly:
**1.4 contains no code reading the real clock.** The composition root that supplies it arrives
with the first route in 1.5, so there is currently no user-facing path that can execute a
command.

## A serious bug, caught by integration testing

`repositories.accounts.findByName` labels each row using the **requested** name rather than the
row's own. The effect: asking for `bank2`, which does not exist, made every returned account
look like `bank2`, so `findAccount` matched the first row and the executor spent from **cash**.

The first test run reported three failures, one of them "an unknown account fails" — passing on
a look. A lookup that silently resolves to the wrong row is the worst failure mode a
persistence layer can have, and it was only visible because the test asserted that an unknown
account *fails*, not merely that a call completes.

Fixed so the stored name always wins, with a regression assertion that a request for a
non-existent account leaves every real balance untouched.

## Atomicity proven with real SQLite, not mocks

A mock repository would pass "these two writes are atomic" while proving nothing, so the
failure cases are produced by the database itself: a `BEFORE INSERT` trigger that raises.

- **Expense**: the insert fails, and the test asserts the account balance is still 50,000 — no
  money vanished without a record.
- **Inventory**: the *quantity* is written first, then the event fails, and the test asserts
  the quantity is still 10 — no unexplained number was left behind.

That second case matters because it exercises the rollback in the harder direction. A test
that only failed the first write would not prove the transaction wraps both.

## Rules amended, not weakened

`hari-os/command-boundary` previously forbade `@/lib/db` in the command layer, which 1.4
explicitly disproved. The rule now permits `@/lib/db/repositories` and continues to block
`connection`, `migrations`, `schema`, and `better-sqlite3`, so the executor can coordinate
storage but cannot open a database or write a query of its own.

ESLint matches the first pattern and does not support gitignore-style negation — I tried the
negated wildcard and it did not work, so the allowed module is enumerated instead. The cost is
that a new non-repository module in `src/lib/db` must be added to the list, which is a visible
review point. Verified with a probe that triggered all four restrictions, then deleted.

**Domain purity was not relaxed for any of this.** `domain/` still imports nothing, and
`hari-os/domain-purity` is unchanged.

## A documentation defect found and corrected

`ARCHITECTURE.md` section 4 stated that `lib/*` never imports from `domain/`. That was already
false when it was written: micro-phase 1.3's validator imports `isMoneyAmount`, `isQuantity`,
and `isAccountName` from the domain, deliberately, so the command boundary and the schema
`CHECK` constraints cannot drift apart. Repositories need the same thing. The rule has been
corrected to describe what the code actually does, with the direction that must not move —
`domain/` imports nothing — called out separately.
