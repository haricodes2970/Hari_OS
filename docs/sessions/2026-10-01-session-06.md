# Session 06 — Phase 7: Skills, Habits, the private log, and the photo path

**Date:** 2026-10-01
**Phase:** 7 — Skills and Habits
**Outcome:** Complete and verified. Phase 8 was not started.

## What this session was for

Phase 6 ended with the Dashboard reading `habit_log` and `SKILLS_AVAILABLE = false` — two
truthful statements about work that did not exist yet. This session built the work, so both of
those statements had to change, and the phase's own scope note allowed a laundry-photo
placeholder. The user's instruction was a real upload path in Phase 7, so no placeholder was taken.

## What was built

### Schema

One migration, `002_screen_time`. `habit_log` was rebuilt with a fourth type and a validated
`minutes` column; `scripts/schema-test.mjs` was updated to expect both migrations, and
`scripts/db-check.mjs` learned to normalise whitespace when matching a constraint, because a
rebuilt table formats its `CHECK` across lines.

`skill`, `skill_log`, and `private_log` already existed. No other table was touched.

### Domain

- `src/domain/skills.ts` — the ten-skill cap, name validation, case-insensitive duplicate
  detection, optional duration, and a per-skill tally with no streak, no score, and no comparison.
- `src/domain/habits.ts` — cooking, dishes, laundry, and screen time; the laundry photo rule;
  streaks; the twice-a-week target; and private entries with their own note limits.
- `src/domain/result.ts` — 13 new codes.

### Persistence

`SkillRepository`, `HabitRepository`, and `PrivateLogRepository` in the existing
`src/lib/db/repositories.ts`. `display.habitsForDate` was deleted, which retired ADR-050's stated
precondition (ADR-054).

### Features

- `src/features/skills/view.ts` — the full list, in stored order.
- `src/features/habits/view.ts` — today's entries, three neutral streaks, the laundry target, the
  screen-time entry, and the photo timeline.
- `src/features/habits/private-log.ts` — the only reader of `private_log` (ADR-052).
- `src/features/habits/photos.ts` — store a laundry photo; read one back (ADR-051).

### Commands

Four new kinds: `skill.create`, `skill.log`, `habit.record`, `private.log`. Fourteen in total.
The contract has no field for a photo and no field for a count, and validation rejects unknown
fields, so a model cannot supply either.

The parser prompt gained the four kinds, the new fields, and fourteen examples — including two
negative ones: an urge is not an occurrence, and a count is not something it reports.

### Photos

`src/lib/storage/photos.ts` reads the first bytes and derives the type and extension from them;
SVG is refused; the size is bounded before the write; the name is a fresh UUID. `POST /api/photos`
and `GET /api/photos/[id]/[filename]` hold no rules of their own — `src/app` may not import
storage, so the feature owns the operation (ADR-055).

### Pages

`/skills` and `/habits`, two navigation items, and the Dashboard's urge entry point now opening the
real list.

## Two defects found by the tests, both fixed

**1. `habitStreak` never ended a streak.** It collected the dates recorded as *done* and walked
back from the most recent one. So a day the user explicitly recorded as not done had no effect at
all: the walk started on the day before it and counted the run above. The function's own comment
said "a day recorded as not done does end it", and the PRD distinguishes "not recorded" from "not
done" for exactly this reason. It now walks from today, skipping today itself because the day is
not over, and stops at any day that is not recorded as done.

**2. A "no" answer grew the private log.** `executePrivateLog` called `insertEntry` with a null
note when `happened` was false. Since `insertEntry` deletes and re-inserts, that rewrote the row
rather than removing it — so correcting a mistaken entry left it in place, and a table of private
entries could never shrink. `PrivateLogRepository.removeForDay` was added and the executor now
deletes.

Both were found by `skills-test.mjs`, not by reading. The first is the more interesting one,
because the code and its documentation disagreed and only a behavioural test could say which was
right.

### Expectations that had to change, and why

Three pre-existing assertions asserted that Skills did not exist. They were the phase's own
truthful-unavailable state, and Phase 7 made them false in the intended way:

- `scripts/dashboard-test.mjs` asserted `skillsAvailable === false` twice and that the model carried
  no skills list. Now: available is `true` **and** the model still carries no list, which is the
  distinction the flag existed for.
- `scripts/dashboard-accept.mjs` asserted the page said "not available yet". Now it asserts the
  entry point opens the real list and says nothing is chosen for the user.
- `scripts/responsive-check.mjs` named the navigation links. Now six.

### Probes

Two new ESLint scopes, `hari-os/skills-boundaries-enforced` and
`hari-os/habits-boundaries-enforced` (ADR-055), with 11 new probes. The Habits scope is the
interesting one: it is the only scope whose persistence group omits `@/lib/storage`, because a
route may not write a file and a feature is the only layer that can. The probe asserts the
permission *and* that the same slice still cannot reach `node:fs` or a database handle beside it.

## Decisions recorded

ADR-051 (photo URL shape and the laundry-only upload), ADR-052 (the private log's structural
boundary), ADR-053 (the photo requirement is a check, not a claim), ADR-054 (the habit read model
replaces the Dashboard's ad-hoc read), ADR-055 (the two new lint scopes).

## Not done, and why

- **Phase 8 was not started.** Its scope is now partly ambiguous: the photo path it was assumed to
  own shipped here. `PROJECT_STATUS.md` records the open question rather than resolving it.
- **A photo diary of anything other than laundry is not buildable.** `habit_log.photo_url` is the
  only column that can hold a picture. An upload for any other type is refused rather than written
  somewhere unreadable.
- **No private-log figure exists anywhere**, by construction rather than by discipline: no function
  in the read side returns a number, the command contract has no field for one, and the Dashboard
  cannot read the table.
