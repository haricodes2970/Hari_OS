# Session — 2026-10-01 (2) — Phase 3, Kitchen

Phase 3 delivered as one unit. This report records what was built, what was verified, and what
was wrong along the way. Nothing here is planned work presented as done.

## Result

Kitchen is a real feature rather than the Phase 1 vertical slice. The user can add an item, set
what counts as low, record use and restock by form or by sentence, read the state, and correct
a mistake without anything being deleted.

**920 assertions pass, 0 fail**, up from 717 at the end of Phase 2. All 12 checks pass, and the
17-step HTTP acceptance run passes end to end.

## What was added

### Domain — `src/domain/inventory.ts`

Five pure functions, all returning `Result`, all tested in memory with no database and no
provider:

- `recountAfterUse` — the PRD's "I had 10 onions, used 2". Takes the two stated facts and
  computes the difference. The model reports 10 and 2; the 8 exists only here.
- `setLowStockThreshold` — accepts `null` for "no threshold" and refuses zero, which would flag
  every item forever.
- `editInventoryDetails` — name and unit. Refuses a unit change while quantity is non-zero,
  because 8 pieces is not 8 kg and there is no unit conversion.
- `reverseInventoryEvent` — the inverse delta, computed from the **current** quantity.
- `findInventoryItemById` — id lookup, which the correction path needs and name lookup cannot
  provide.

A pre-existing inverted condition in the zero-normalisation was fixed while adding these.

### The compound sentence

`inventory.recount_after_use` was threaded through the whole pipeline: contract, validation,
executor, domain input, parser allowlist, and the parser prompt. The prompt change matters — the
model previously dropped the initial count in "I had 10 onions, used 2" and produced only a
consumption, which would have left the stock wrong by the 10 the user actually said.

The kind carries two facts and no result, for the reason given in ADR-040: a model has no
business performing arithmetic that affects a quantity.

### Persistence — `src/lib/db/repositories.ts`

`insertItem` (with its opening-quantity event), `nextItemId`, `findById`, `saveDetails`,
`saveLowThreshold`, `findEvent`, `recentInventoryEvents`. No migration was needed; the schema
arrived in micro-phase 1.1 and `npm run db:check` is unchanged.

### Feature and routes

- `src/features/kitchen/setup.ts` — add, rename, set threshold.
- `src/features/kitchen/correction.ts` — the correction, executed through `runCommand`.
- `src/features/kitchen/view.ts` — the read side.
- `src/app/api/kitchen/route.ts` — `POST` for the four maintenance operations, `GET` → 405.
- `src/app/kitchen/page.tsx`, `src/components/KitchenForm.tsx` — the page.
- `src/features/shared/same-origin.ts` — ADR-042's guard, extracted so both write routes share
  one implementation instead of two copies that could drift. The parse route now imports it.
- `nowTimestamp()` in `command-runtime.ts`, keeping `new Date()` confined to the approved
  boundary.

## Decisions recorded

- **ADR-043** — the third endpoint, and why it cannot execute a command.
- **ADR-044** — a correction is a reversal, never a deletion or an overwrite.

ADR-036 claimed `POST /api/commands` was the only entry point. Phase 3 added a route that
reaches only maintenance operations. Rather than quietly rewriting ADR-036, ADR-043 records the
narrowing and the property that still holds: one path to the executor.

### HTTP acceptance, 17 steps

Run against a disposable database at `/tmp/kilo/e2e/kitchen.db` with
`HARI_OS_DB_PATH` set before any import, served by `next start` on port 3222. The development
database's SHA-256 was checked before and after the whole run and is unchanged.

1. The Kitchen page loads and renders.
2. Adding an item stores it with its opening quantity and threshold.
3. Setting the quantity to 10 and the threshold to 3 persists both.
4. "used 2 onions" leaves **8**, and writes one event.
5. After a reload the quantity is still 8 — it is persisted, not held in the page.
6. "used 5 onions" leaves **3**.
7. The Dashboard lists onions under low stock at exactly 3 against a threshold of 3 — the
   boundary case, at the threshold rather than below it.
8. Restocking 5 returns it to 8 and the Dashboard's flag **disappears**.
9. Consuming 999 from 8 changes nothing: quantity stays 8, the event count does not move.
10. Consuming 1 **kg** of an item tracked in **pieces** changes nothing. No silent conversion.
11. Correcting the `−5` entry returns the item to 8.
12. The original `−5` is **still in the log**, with the correction beside it as `+5` labelled
    `correction of entry #5`.
13. **The invariant holds: the sum of all six deltas equals the stored quantity, 8.** A
    correction that reversed against a stale snapshot would not satisfy this.
14. A correction that is no longer possible — reversing a `−5` against a current quantity of 2 —
    is refused rather than approximated.
15. Failures carry closed-set tokens. No item name the user typed appears in any redirect URL.
16. `GET /api/kitchen` is 405; a cross-origin `POST` is 403; a malformed body is 400.
17. The page shows the corrected quantity and the full six-entry history after reload.

### Four test assumptions that were wrong, and were corrected

These were errors in the tests, not in the code. Each was fixed by changing the test to assert
the real behaviour, and each is worth recording because in three cases the honest behaviour was
the less obvious one.

- **Near-miss item matching** was tested with trailing whitespace, which the normaliser handles.
  Replaced with the cases that actually matter: prefix and plural forms.
- **`reverseInventoryChange` was expected to restore 8.** It restores 10, and 10 is correct —
  reversing the `−5` against the current 8 gives 13, and the test was asserting against a
  different event. The domain was right.
- **The recount refusal** was written as a count of 3 with a use of 2. That is valid input.
  The genuinely invalid case is a use larger than the count, and that is what is now tested.
- **The correction sign** was asserted to reject `insufficient_inventory`. A reversal that would
  drive stock below zero must indeed be refused, so the test now asserts the real
  reason.

## Not verified

- **A live OpenRouter call.** Unchanged from Phase 2. No `OPENROUTER_API_KEY` was available, so
  the sentence path is proven against a local HTTP stub and an injected transport, not against
  the real model. The Kitchen page correctly reports that parsing is unavailable, which is the
  degraded mode ADR-041 describes.
- **The parser prompt's handling of a compound sentence is unproven against a real model.** The
  prompt now instructs the model to report both the count and the use. Whether it complies is a
  question only a live call can answer.

## Carried forward, unchanged

- The expense ledger still cannot record a correcting entry. `expense` holds non-negative spends
  only, so a fix needs a migration. Inventory corrections now exist; this one does not.
- An account still reads `₹0.00` until one is spent from, because there is no command to set an
  opening balance.
- The two pre-existing lint configuration gaps recorded in Phase 2 are untouched: `src/lib/db`
  may import `@/commands/parser`, and `src/commands` may import
  `@/features/shared/command-runtime`. Neither is exercised. Closing them is an architecture
  change and needs an ADR.
- The PRD-versus-roadmap scope divergence in `ROADMAP.md` is still unresolved and is the user's
  call.
- The baseline database fingerprint discrepancy recorded in 1.5 remains unexplained.

no expense page change was made in this session. The only expenses code touched is the shared
`command-runtime.ts` and the shared origin guard, both of which the Kitchen work required.

The PRD's "what can I cook with current stock" view was not built. It is later work by the PRD's
own wording, and it remains the main thing this phase deliberately left out.
