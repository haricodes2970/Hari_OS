# Session — 2026-10-01 (4) — Phase 5, Dashboard

Phase 5 delivered as one unit. This report records what was built, what was verified, what was
deliberately left unbuilt, and the one discrepancy found. Nothing here is planned work presented
as done.

## Result

The Dashboard is a real, persisted, daily command center assembled from application state that
already existed. Low stock and today's spend come from the modules that own them. The three cards
whose modules do not exist say so, in the product, instead of showing an empty list.

**1253 assertions pass, 0 fail** across 10 suites, up from 1177 across 9. **39 architecture
probes** pass, up from 27. A **57-check HTTP acceptance run** and a **29-check headless-browser
responsive run** pass. All of `format:check`, `typecheck`, `lint`, `build`, and `db:check` pass
with 0 errors and 0 warnings.

## The honest finding

**The missing part of the Dashboard was five later phases, not one screen.** The PRD's Dashboard
is six cards: top 3 tasks, suggested first action, low stock, dishes/laundry, today's spend, and
an "I feel like scrolling" entry to Skills. Two of the five modules behind those exist. Filling
the other three would have been Routine, Skills, and Habits built as decoration, which is exactly
what the phase boundary forbids.

So the work was: make the screen complete from real state, and make "not available yet" a
supported product state rather than a gap in the documentation.

## What was added

### The read model — `src/features/dashboard/view.ts`

`readDashboard(date)` is the only thing the page reads. It composes four sources and owns no rule:

| Shown | Source | Rule |
| --- | --- | --- |
| Low stock | `listKitchenStock()` | the domain's `isLowStock` |
| Today's spend | `readDailyBill(date)` | the domain's `summariseDay` |
| Tasks | `display.tasksForDate(date)` | none — first three, true count kept |
| Dishes and laundry | `display.habitsForDate(date)` | none — rows, or "not recorded" |

Two figures are the same number **by construction** rather than by agreement. The Dashboard's
spend and the daily bill's total both come from `summariseDay` over the same rows. The
repository's SQL aggregate `spendForDate` exists and is deliberately not used here: a second way
to total a day is the disagreement Phase 4's architecture notes warn about, and a test asserts
the read model never calls it.

`readDashboardSummary` moved out of `src/features/shared/queries.ts`. That file holds the
Kitchen page's inventory projection; a Dashboard that aggregates three features is not a shared
helper, and leaving the old name in place would have allowed two definitions of "what the
Dashboard shows" to drift apart. `scripts/kitchen-test.mjs` section 42 was updated to import the
new one — same assertions, new owner.

### Truthful states, not empty lists

- **Tasks.** `plan_task` has been in the schema since micro-phase 1.1, so real rows are read and
  displayed. Nothing in `src/` writes one, so the list is empty and the page says Routine is not
  built — it does not imply a good day or a bad one.
- **Suggested first action.** The first task the user wrote down that is not marked done. It is
  not ranked, not scored, not generated, and absent when nothing is planned or everything is
  done. The two cases are rendered differently, using the task list, precisely so that `null`
  never has to mean "everything is fine".
- **Skills.** A build constant, `SKILLS_AVAILABLE = false`, rendered as an unavailable entry
  point. No route was created for a module that does not exist, and no replacement activity is
  ever chosen.
- **Dishes and laundry.** `habit_log` exists, so its rows are read. A missing row renders as
  **not recorded** — a claim about the data — rather than **not done**, which would be a verdict
  about the user's day. Nothing writes a habit row, so that distinction is currently the whole
  content of the card, and saying so is the honest thing to do.

### The page

Ordered by the four questions: what happened (the shared input), what matters today (tasks and
first action), what needs attention (low stock), what changed (today's spend), then the
unavailable cards. Black-on-white, the existing rules only, no new component, no client
JavaScript, no animation. It renders on a database that has been migrated and never set up.

### Two new enforced boundary scopes

`src/features/dashboard/**` may not import `@/lib/db`, `better-sqlite3`, `node:fs`, a provider
module, `@/commands/executor`, or a feature's write side. `src/app/**` may not import `@/lib/db`,
`better-sqlite3`, `node:fs`, or the provider's config and transport; `next/server` is exempt,
because every route handler needs it and a framework import is not storage access.

Both are probed the way ADR-046 established — each rule is asserted to fire **and** the imports
the architecture permits are asserted to still pass, because a rule that rejected everything
would otherwise satisfy the probe. 39 probes, up from 27.

## One discrepancy found, and recorded rather than fixed

`ARCHITECTURE.md` section 15 states: "A threshold of zero is refused. It would flag every item
forever." **The code does not refuse it.** `setLowStockThreshold` accepts zero, and
`isLowStock` then flags the item only while its quantity is zero.

`scripts/dashboard-test.mjs` asserts the behaviour that actually exists — zero flags at zero, not
one piece above it — and the documentation now carries a dated note recording the mismatch. Per
`AGENTS.md` §2, neither the code nor the documentation was silently changed to match the other.
Deciding which one is right is the user's call: the code's behaviour is defensible (a threshold of
zero is a real "tell me when I am out"), and the documented rule is defensible (a zero threshold
is more likely a mistake). Fixing it would change Kitchen behaviour, which Phase 5 was not
assigned to do.

### What the acceptance run proves that the unit tests cannot

`src/app/page.tsx` is a Server Component. It cannot be rendered by `react-dom/server` in a bare
Node process — `renderToStaticMarkup` throws on the first async child — and inspecting the
element tree would show nothing about the HTML a browser receives. So the page claims are checked
the only honest way: a real `next start`, real HTTP, a real disposable database. That run starts
on a **completely fresh** database, asserts the empty states, then runs the documented
`npm run db:setup` against that same file, then consumes, restocks, spends, reloads, and
compares the rendered total against the fetched bill text.

### Responsive was measured, not eyeballed

Phases 2–4 recorded "responsive" as a viewport export in `layout.tsx`. That is groundwork, not
verification. Phase 5 drives headless Chrome over the DevTools protocol and measures the rendered
document at 320, 390, and 1440px: `scrollWidth <= clientWidth`, no element extending past the
viewport, the day's total present at a readable size, the shared input and button on screen, and
navigation intact. If no browser is found the script fails loudly rather than reporting a pass it
did not earn.

What it does **not** do: it takes no screenshots, checks no contrast or focus order, and is not a
substitute for looking at the page. I could not view the rendered screenshots in this session —
the model has no image input — so the visual check here is the measured DOM plus the extracted
text, not a picture.

### A real gap the measurement exposed

The shared natural-language input had **no CSS at all**. Phase 2 added `.chat`, `.chat-row`,
`.chat-input`, `.chat-echo` to the markup and never styled them, so on every page the one control
the PRD calls "low friction" rendered as a bare input and button at the top of the screen. Six
rules in the existing black-on-white language fix it: a bordered block, a wrapping row, an input
that flexes and never forces a minimum wider than the screen, and a muted echo line for the
sentence the parser read. No colour that is not already in the file, no animation.

## Not verified

- **A live OpenRouter call.** Unchanged from Phases 2, 3, and 4. No `OPENROUTER_API_KEY` has
  been available, so the Dashboard correctly reports that parsing is unavailable and the input is
  disabled. The sentence path is proven against a local stub and an injected transport.
- **How the page looks.** Measured, and read as text; not reviewed as an image, for the reason
  above.
- **Every future-module card against real data.** Tasks and habits are tested with rows inserted
  the way their future phase would write them, since nothing in `src/` writes them yet. Skills
  has no data path at all, by design.

## Deliberately deferred, by decision

- **Routine, Sleep, Skills, Habits, Photo Diary.** Phases 6–8, untouched. The Dashboard states
  each one's availability rather than approximating it.
- **The "what can I cook" view.** Phase 8, per the roadmap. The Kitchen page keeps the state that
  view would need.
- **Any recommendation, ranking, streak, or score.** The PRD's principle is that the assistant
  organises and the user decides. `suggestedFirstAction` is the first undone task or nothing.
- **A Dashboard endpoint.** It is read-only. There is no route, no server action, and no
  repository call from a page.
