# Session — 2026-10-01 (3) — Phase 4, Expenses

Phase 4 delivered as one unit. This report records what was built, what was verified, and the two
defects found along the way. Nothing here is planned work presented as done.

## Result

The PRD's expense ledger is complete: three accounts, a recorded spend reducing exactly the right
one, money arithmetic that cannot drift, visible history, a day's spend calculated from persisted
rows, and the daily bill as deterministic shareable text.

**1177 assertions pass, 0 fail**, up from 920, plus 27 architecture probes. All 15 checks
pass, and the 25-step HTTP acceptance run passes end to end.

## The honest finding

**Most of Phase 4 already existed, and the missing part was smaller than the brief implied.** Phase 1
wrote the money domain, the closed three-account model, the `expense.record` contract, and an
atomic executor. Phase 2 wrote the parser. The Dashboard already had a "Spent today" tile. The
Expenses page already showed balances and history.

So this phase verified rather than rebuilt that work, and the audit turned up more than expected:

- **The endpoint that spends money had no CSRF guard** (ADR-045).
- **The documented layer boundaries were not enforced at all** (ADR-046).

Both are detailed below. Neither is a Phase 4 regression; both had been latent since Phase 1.

## What was added

### The daily bill — `src/domain/expenses.ts`

`summariseDay` reads a day's rows and returns the total, the breakdown by item, and the breakdown
by payment method. Three properties make it trustworthy:

- **The breakdown reconciles with the total by construction.** Both breakdowns are partitions of
  the same entries.
- **Every sum goes through the domain's own `addMinorUnits`,** which refuses an addition past the
  exact integer range. `SUM(amount)` would have returned a float and lost a paisa quietly.
- **The ordering is total**, so the same ledger always produces the same text: lines by amount then
  label, grouping case-insensitively, and the displayed spelling chosen alphabetically rather than
  by row order.

The date boundary is applied in the domain *and* in SQL. Duplicating it is deliberate — the domain
must be correct even when handed unfiltered rows — and a test asserts the two agree.

### The shareable bill — `src/features/expenses/bill.ts`, `GET /expenses/daily-bill`

Every character of the bill text comes from persisted rows through `formatMinorUnits`. No model
writes any of it. Served as `text/plain` from a `GET`, so it can be selected, copied, saved, or
opened in a mail app with scripting disabled — this application has no client JavaScript, and a
copy button would have been its first client component to save three keystrokes. It is a read, so
it needs no origin guard.

### The page

Balances, today's total, both breakdowns, the recent-expense history, and a link to the bill.
Empty states for no accounts, no expenses, and accounts at zero. An explicit note that a day's
spend is not an account balance, and an explicit note that a wrong expense cannot be corrected
today — so the gap is visible in the product rather than only in this report.

### Repository and tests

`display.expensesForDate(date)` returns a day's rows for the bill's breakdown. No migration: the
`account` and `expense` tables arrived in micro-phase 1.1 and `db:check` is unchanged.

`scripts/expenses-test.mjs` — 257 assertions, focused on account resolution, money precision,
atomicity, and the bill.

## Two defects found and fixed

### ADR-045 — `POST /api/commands` had no origin guard

ADR-042 added an origin check so another site could not submit a command. Phase 3 reused it for
`POST /api/kitchen`. **Nobody had put it on `/api/commands`** — the endpoint ADR-036 names as the
only way a command enters the application.

Any page the user had open could `POST` an `expense.record` to `localhost` and record a spend
against a real account. V1 has no session and no cookie, so nothing in the request identifies it
as the user's own, and the `303` redirect meant the victim's browser followed the response and saw
nothing wrong.

Phase 4 is what made this matter: before it, the endpoint moved ₹10 of stock at a time. It now
moves money. The guard is applied before the body is read, and all three write routes share one
implementation.

### ADR-046 — the architecture rules were reported but not enforced

`AGENTS.md` states the layer boundaries are "enforced, not merely documented". Probing each claim
by writing a file that imports the forbidden module and linting it:

| Claim | Result |
| --- | --- |
| `src/domain` cannot import `@/lib/db` | **not blocked** |
| `src/domain` cannot import `better-sqlite3` or `node:fs` | **not blocked** |
| `src/lib/validation` cannot import the database | **not blocked** |
| `src/commands` cannot import `better-sqlite3` | **not blocked** |
| `src/components` cannot import `@/lib/db` | **not blocked** |
| `src/domain` cannot import the provider | blocked |
| `src/domain` cannot read the clock (`Date.now()`) | blocked |

**Cause.** In ESLint flat config, two config objects that set the *same rule* for the *same files*
do not merge — the later one replaces the earlier wholesale. `src/domain` was covered by three
configs; `provider-boundary` came last, so only its provider patterns applied. `src/features/chat`
had a single config covering it, and was the only fully enforced scope.

**Fix.** One consolidated config per scope, appended last, carrying the union of every pattern that
scope was meant to enforce. Nothing intended-forbidden becomes permitted; every group already
existed in the file.

**The result worth having:** `npm run lint` passed the moment the rules were armed, so **no source
change was needed**. The architecture was being upheld by discipline, not by tooling — and nothing
could tell the difference, because every test in the project also happened to comply.

`npm run architecture:probe` now asserts each rule fires *and* that the imports the architecture
permits still pass, because a rule rejecting everything would otherwise satisfy it.

### Four test assumptions that were wrong, and were corrected

Recorded because in three cases the honest behaviour was the less obvious one.

- **`parseCommand` failures were asserted by summary code.** Every refusal reports
  `invalid_command` and lists issues underneath, so asserting only the summary passed for the
  wrong reason — an invented account name and a missing field looked identical. Now asserts the
  specific issue.
- **A payment-method breakdown line was expected to be `bank1`.** Cash was larger in that fixture.
  The test was wrong; the ordering was right.
- **My own test spread an `expect` field into a command object** and it was correctly refused as
  an unexpected field. A nice demonstration that the allowlist works, and a bug in the test.
- **`releaseDatabase()` was called mid-file**, which permanently closes the shared handle and broke
  every later query. It is only for teardown.

### Two probes that were wrong before the finding was

Worth recording, because both first reported a defect that was not there.

- The `server-only` probe used a directory named `__probe-client`. Next.js does not route
  underscore-prefixed folders, so the build never saw it. The second attempt used a stale `.next`
  cache. The third, with a routable directory and a clean build, failed as required — the
  boundary is genuinely enforced.
- An early boundary probe passed `--rule '{}'` to silence an unused-import warning, which
  **replaced the config's rules entirely** and made every rule look inert. That produced a
  nine-rule "did not fire" result that was an artefact of the probe. The real defect was found
  only after removing it.

## Not verified

- **A live OpenRouter call.** Unchanged from Phases 2 and 3. No `OPENROUTER_API_KEY` was
  available, so the sentence path is proven against a local HTTP stub and an injected transport.
  The expenses page correctly reports that parsing is unavailable.
- **How a real model handles the expense sentences.** The prompt carries worked examples for
  "bought banana 10 rupees cash", "spent 50 on groceries using cash", "paid 100 from bank1 for
  groceries", and "spent ₹250 on vegetables from bank2", and the allowlist, validation, and domain
  conversion are each proven independently — but only a live call can show whether a real model
  complies.

## Deliberately deferred, by decision

- **Expense correction and refund.** The PRD asks for wrong entries to be easy to undo. `expense`
  has `CHECK (amount >= 0)` and no `source_text`, so a reversal has nowhere to live. Two options
  were assessed — an additive `account_event` log table, or relaxing the amount check — and
  **deferred**, because no refund model was requested and inventing one is an accounting project,
  not an expense feature. The page says so in its own words.
- **Batch entry.** The PRD contradicts itself: section 6.4 says it is supported, section 5 says it
  comes later, and Phase 2's accepted ADR commits to one sentence, one command. Deferred and
  recorded rather than quietly resolved.
- **Setting an opening balance.** Accounts open at zero through `npm run db:setup`, which is the
  PRD's "set manually at the start". No account-management UI was invented; the V1 model is three
  named accounts and the schema enforces that.
