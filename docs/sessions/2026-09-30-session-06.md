## Bugs found and fixed during this micro-phase

These were found by testing, not by reading. Each is now covered by a regression assertion.

**1. Money conversion would have corrupted inventory.** `amount` means money in minor units
on `expense.record` and a quantity of stock on `inventory.consume` and `inventory.restock`.
The route handler first converted every `amount` through `toMinorUnits`, which would have
multiplied "2 onions" by 100 and restocked two hundred of them. The conversion is now chosen
by command kind, never by field name.

**2. The form did not work without JavaScript.** The first `CommandForm` used
`useActionState`. React replaces a form's `action` attribute with a stub when it owns
submission, so the rendered markup contained
`action="javascript:throw new Error('React form unexpectedly submitted.')"` and the form
worked *only* with scripts enabled. The enhancement had quietly become the requirement. The
client component was deleted and replaced with a plain server-rendered form.

**3. An empty amount would have become a free expense.** `Number("")` is `0`, so a loose
conversion would have recorded a zero-cost expense from an empty field. `formToCommand`
forwards anything that is not recognisably a number as raw text, so validation rejects it and
names the field.

**4. Every page returned HTTP 500 on a new database.** `getDb()` created the file but never
applied the schema, so every query failed with `no such table: inventory_item`. This
violated the PRD's requirement that empty states must not crash. `getDb()` now migrates on
open; row creation stays in the explicit setup script.

**5. A probe that tested nothing.** The first `server-only` probe was written to
`src/app/__probe-client/`. Next ignores directories beginning with `_`, so the route was
never compiled and the build passed — a false verification. Re-run as `probe-client`, the
build correctly fails with exit 1.

### Manual acceptance flow

Run against a production build with `HARI_OS_DB_PATH` pointed at a disposable database, driven
with `curl`. Every step below was executed and the stated result observed.

1. Dashboard renders: spend `₹0.00`, `milk` reported low at 1 litre against a threshold of 2.
2. Kitchen renders `onions` at 10 piece, OK.
3. Consume 3 onions → `303` to `/kitchen?saved=ok`.
4. Re-fetch: `onions` now **7** piece. Persisted across a fresh page load.
5. Record `banana`, 50 rupees, cash → `303` to `/expenses?saved=ok`.
6. Expenses page: cash **-₹50.00**, ledger row `2026-09-30 16:45 · banana · cash · ₹50.00`.
7. Dashboard: today's spend **₹50.00**, "Across 1 entry."
8. Restock 4 onions → 11. Recount to 12 → 12. Both persisted.
9. JSON call with `amount: 1250` produced `-₹12.50`, confirming minor units pass through
   unscaled.

## Known limitations, carried forward

- The expense ledger cannot record a correcting entry; `expense` holds non-negative spends
  only. Unchanged since 1.2 and needs a migration.
- There is no command to create an inventory item or set an opening balance, so both come from
  `npm run db:setup`. An account reads `₹0.00` until one is spent from. Opening balances are
  zero deliberately: inventing a figure would be the kind of fabrication the PRD forbids.
- The Dashboard task list renders but nothing creates `plan_task` rows, so it is always empty.
  Out of Phase 1 scope.
- Expense correction, natural-language input, and the LLM remain out of scope. Phase 1 has no
  parser and no model integration.
